### Step 3: TLS
* Ingress terminates TLS on port 443 using secret `http-echo-tls`.
* `nginx.ingress.kubernetes.io/ssl-redirect: "true"` redirects HTTP to HTTPS.
* `templates/tls-secret.yaml` generates a self-signed certificate (Helm `genSelfSignedCert`) for the host. `lookup` reuses the existing secret on upgrades, so the certificate does not change on every deploy.
* For production, set `ingress.selfSignedTLS.enabled=false` and use cert-manager (add the `cert-manager.io/cluster-issuer` annotation) or a pre-created secret.

## TLS: implementation, flow and production path

### How TLS is implemented in this chart
TLS is terminated at the ingress. The pods themselves still speak plain HTTP.

| Piece | Where | What it does |
|---|---|---|
| `ingress.tls` | values.yaml | Lists the hosts and the Kubernetes secret that holds the certificate (`http-echo-tls`) |
| `spec.tls` | templates/ingress.yaml | Renders `ingress.tls` into the Ingress so ingress-nginx serves HTTPS on port 443 for that host |
| `ssl-redirect: "true"` | ingress annotation | ingress-nginx answers plain HTTP with a 308 redirect to HTTPS |
| `templates/tls-secret.yaml` | chart | Generates a self-signed certificate for the host (Helm `genSelfSignedCert`), stored as a `kubernetes.io/tls` secret |
| `lookup` in tls-secret.yaml | chart | If the secret already exists, its certificate and key are reused, so `helm upgrade` does not rotate the certificate on every deploy |
| `ingress.selfSignedTLS.enabled` | values.yaml | Switch for the generated certificate. Set it to `false` when using cert-manager or your own secret |

### How a request flows
1. The browser or curl resolves `http-echo.k8s-server.local` (locally via /etc/hosts to 127.0.0.1, with `minikube tunnel` exposing the ingress).
2. On port 443 the TLS handshake starts. The client sends the hostname (SNI), and ingress-nginx picks the certificate from the `http-echo-tls` secret for that host.
3. ingress-nginx decrypts the traffic and forwards it as plain HTTP to the Service `http-echo` (TCP 5678), which load-balances across the pods.
4. It adds `X-Forwarded-Proto: https` and `X-Forwarded-Port: 443`, which is visible in the echo response and proves TLS was terminated at the ingress.
5. A request to port 80 gets a 308 redirect to the https URL.

If the secret is missing, ingress-nginx falls back to its built-in "Kubernetes Ingress Controller Fake Certificate", which is a quick way to spot a misconfigured secret.

### Limits of the self-signed certificate
* Browsers do not trust it, hence the "Not Secure" warning and `curl -k`. The connection is still encrypted.
* It is valid for `ingress.selfSignedTLS.validityDays` (365) and is not renewed automatically.
* The private key is generated by Helm and stored inside the Helm release data in the cluster.
* `lookup` returns nothing in `helm template` and client-side dry runs, so those always show a fresh certificate.
* Suitable for local testing only.

### Moving to a production certificate

**Option A (recommended): cert-manager with Let's Encrypt, automatic issuance and renewal**

Requirements: a real public DNS name that points at the ingress. A `.local` name cannot get a public certificate.

1. Install cert-manager:
```bash
   helm repo add jetstack https://charts.jetstack.io
   helm install cert-manager jetstack/cert-manager \
     --namespace cert-manager --create-namespace --set crds.enabled=true
```
2. Create a ClusterIssuer:
```yaml
   apiVersion: cert-manager.io/v1
   kind: ClusterIssuer
   metadata:
     name: letsencrypt-prod
   spec:
     acme:
       server: https://acme-v02.api.letsencrypt.org/directory
       email: you@example.com
       privateKeySecretRef:
         name: letsencrypt-prod-account-key
       solvers:
         - http01:
             ingress:
               ingressClassName: nginx
```
3. Deploy with a production values file (`values-prod.yaml`):
```yaml
   ingress:
     annotations:
       cert-manager.io/cluster-issuer: letsencrypt-prod
       nginx.ingress.kubernetes.io/ssl-redirect: "true"
     hosts:
       - host: echo.example.com
         paths:
           - path: /
             pathType: Prefix
     tls:
       - secretName: http-echo-tls
         hosts:
           - echo.example.com
     selfSignedTLS:
       enabled: false
```
```bash
   helm upgrade --install http-echo ./http-echo -f values-prod.yaml
```
4. How it works: cert-manager sees the annotation on the Ingress, requests a certificate, proves domain ownership (HTTP-01 challenge served through the ingress), writes the result into the `http-echo-tls` secret, and renews it before it expires (about 30 days before). No chart changes are needed because the chart already references the secret.

Notes:
* Use the `letsencrypt-staging` server first to avoid rate limits.
* If the secret was previously created by this chart's self-signed template, Helm removes it on the upgrade (it no longer renders it) and cert-manager creates the new one. A brief interval with the fallback certificate is possible, so do it in a maintenance window or use a new secret name.
* For internal or wildcard domains use a DNS-01 solver (Route53, Cloudflare, etc.) or a private CA issuer instead of HTTP-01.

Verify:
```bash
kubectl get certificate
kubectl describe certificate http-echo-tls
curl -v https://echo.example.com/        # no -k needed, issuer is Let's Encrypt
```

**Option B: bring your own certificate (corporate CA or purchased certificate)**
```bash
kubectl create secret tls http-echo-tls --cert=tls.crt --key=tls.key
```
Set `ingress.selfSignedTLS.enabled=false` and keep `ingress.tls` pointing at that secret. Renewal is manual, so use External Secrets or Sealed Secrets to manage it safely in GitOps.

**Option C: terminate TLS at a cloud load balancer** (ACM, Google-managed certificates). Then the ingress/Service sit behind it and the chart's TLS block is not needed.

### Additional production hardening
* Restrict protocols and ciphers in the ingress-nginx ConfigMap (for example `ssl-protocols: "TLSv1.2 TLSv1.3"`).
* Enable HSTS once HTTPS is confirmed stable.
* Never commit private keys to git, and keep issuer credentials in a secret manager.
* Monitor certificate expiry (cert-manager exposes Prometheus metrics).

### Production hardening and efficiency
* 2 replicas plus a PodDisruptionBudget (`minAvailable: 1`)
* Runs as non-root, read-only root filesystem, all capabilities dropped, seccomp RuntimeDefault, no privilege escalation
* Small CPU and memory footprint, memory limit set, HPA available (`autoscaling.enabled=true`)
* Real health probes so traffic only reaches ready pods

## 2. How it works now

    curl https://http-echo.k8s-server.local
      -> /etc/hosts resolves the name to the cluster entry point
      -> ingress-nginx controller (port 443, TLS terminated with secret http-echo-tls)
      -> Service http-echo (ClusterIP, TCP 5678)
      -> echo-server pods (PORT=5678) -> JSON describing the request

## 3. macOS: install and run

### 3.1 Install the tools
```bash
# Homebrew (skip if already installed)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

brew install minikube kubectl helm
brew install --cask docker        # Docker Desktop, used as the minikube driver
open -a Docker                    # start Docker Desktop, wait until it says "running"
```
Check: `minikube version && kubectl version --client && helm version && docker info`

### 3.2 Option A: automated
```bash
cd http-echo
./setup.sh
```
On macOS with the Docker driver the script maps the hostname to 127.0.0.1 and tells you to start the tunnel. In a second terminal run `minikube tunnel` (it asks for your password and must stay open), then rerun `./setup.sh`.

### 3.3 Option B: manual
```bash
minikube start --driver=docker
minikube addons enable ingress
kubectl -n ingress-nginx rollout status deploy/ingress-nginx-controller

helm lint ./http-echo
helm install http-echo ./http-echo --dry-run=server      # validation only
helm install http-echo ./http-echo --wait
kubectl get pods,svc,ingress

echo "127.0.0.1 http-echo.k8s-server.local" | sudo tee -a /etc/hosts

# second terminal, keep it open:
minikube tunnel

# first terminal:
curl -i  http://http-echo.k8s-server.local/     # 308 redirect to https
curl -k  https://http-echo.k8s-server.local/    # JSON response
helm test http-echo
```
Open https://http-echo.k8s-server.local/ in a browser and accept the self-signed certificate warning.

### 3.4 Cleanup
```bash
helm uninstall http-echo
minikube delete
sudo sed -i '' '/http-echo.k8s-server.local/d' /etc/hosts
```

## 4. Troubleshooting
* Pods Pending: `kubectl describe pod <pod>` and check the resource requests
* Pod CrashLoopBackOff: `kubectl logs <pod>`. If the cause is the read-only filesystem or the user ID, relax `securityContext` / `podSecurityContext` in values.yaml
* Ingress has no address or curl hangs: make sure `minikube tunnel` is running and /etc/hosts points to 127.0.0.1
* Install fails with an admission webhook error: wait a few seconds for ingress-nginx to finish starting and retry
* Port 80/443 already in use on the Mac: stop the local service that uses them, then restart the tunnel
